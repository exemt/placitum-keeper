# Placitum keeper

[English](README.md) · Русский

Истина активных наборов Placitum: блокировки, списки адресов и ключи лимитов — всё, что меняется на
ходу и должно быть одинаковым на всех узлах.

Инспектор подаёт сигнал внести адрес в набор — запрос приходит сюда. Keeper применяет её в памяти,
кладёт запись в хранилище, публикует дельту и отвечает. Зеркала в инспекторах и на узлах
подхватывают дельту и живут дальше своим составом.

```
инспектор ──► waf.sets.<набор>.event ──► keeper ──► запись в PostgreSQL
                                            │        пакет во внутренний Redis
                                            └──────► дельта всем зеркалам
```

Почему отдельный процесс, а не контроллер: состав наборов меняется тысячами записей в секунду, и
у этого потока другой ритм, чем у конфигурации. Контроллер здесь такой же клиент, как инспектор.

## Сборка и запуск

```sh
docker build -t placitum/keeper .
```

Что нужно рядом, настройки и потолки — в [INSTALL.ru.md](INSTALL.ru.md).

## Шина и HTTP

| Subject | Вид | Что |
| --- | --- | --- |
| `waf.sets.<набор>` | publish | `diff` со ссылкой на пакет изменений в Redis и `tick` раз в 2 с |
| `waf.sets.<набор>.snapshot` | request | зеркало запрашивает ссылку на снапшот |
| `waf.sets.<набор>.event` | request или publish | писатель добавляет или снимает значения; в ответе `seq` или ошибка |
| `waf.keeper.define` | request | контроллер требует перечитать определение набора |
| `waf.keeper.reload` | request | сверить все определения |
| `waf.keeper.lookup` | request | `{set, value}` → `{found, exp}`, не для пути запроса |

Состав передаётся через внутренний Redis, а не по шине: пакеты изменений лежат под
`waf:diff:<набор>:<seq>`, снапшоты — под `waf:snap:<набор>:<epoch>:<seq>`.

Запись принимается целиком или целиком отклоняется. Ошибки: `unknown_set`, `full`, `wrong_type`,
`too_long`, `no_origin`, `no_ttl`, `forever`, `bad_op`, `store_unavailable`, `not_ready`,
`overloaded`.

HTTP на `:8094`: `GET /healthz` (`503`, пока наборы загружаются), `GET /sets` со сводкой наборов,
`GET /sets/<имя>` со ссылкой на снапшот.

## Что нужно знать

- **Хранилище — база контроллера.** Своей у keeper нет: записи, размеры и поиск по ним читаются
  оттуда, а состав живёт в памяти и в пакетах внутреннего Redis.
- **Ответ обязателен.** Отправитель ждёт его: ошибка (`full`, `store_unavailable`) — это строка в
  журнале инспектора, а не тишина.
- **Один процесс на установку.** Keeper — секвенсор: порядок записей определяет он, и вторая
  копия означала бы две правды. Масштабируется конвейером внутри, а не репликами.
